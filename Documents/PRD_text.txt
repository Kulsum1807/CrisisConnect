IntroductionProject nameCrisisConnectProject typeFull-stack web application with real-time featuresDomainEmergency response, incident management, real-time communicationTechnology familyMERN: MongoDB, Express.js, React, Node.js (plus Socket.IO for real-time)Primary purposeA technically strong, explainable portfolio project for SDE placement interviewsSecondary purposeA realistic model of how a coordinated emergency platform can be engineered1.1 One-paragraph summaryCrisisConnect connects people who need emergency help with available responders and administrators. A person can press an SOS button or file a detailed report; the system captures their location, creates a tracked incident, notifies nearby verified responders in real time, lets one responder accept it, and then supports live status updates, incident-specific chat and live responder location until the incident is resolved. Administrators oversee everything, verify responders, assign incidents and view analytics. Every incident is stored permanently with a full history.1.2 Core flowEmergency reported -> Location captured -> Incident created (PENDING)   -> Nearby available responder notified -> Responder accepts   -> Real-time coordination (status, chat, live location)   -> Incident resolved -> Complete history storedNoteCrisisConnect is a prototype for learning and demonstration. It does not replace official emergency services. The application must display a clear notice: in a real emergency, call the local emergency number (112 in India).1.3 MotivationReal-world relevance: emergency coordination is a problem everyone understands, which makes the project easy to explain in an interview.Technical depth: it forces real engineering decisions (state machines, role-based access, geospatial queries, WebSockets, concurrency) rather than simple CRUD.Learning goal: the developer must understand every layer well enough to defend design decisions without relying on generated explanations.2. Background: The Previous PrototypeCrisisConnect began as a prototype using React, Vite, React Router, React Leaflet and Socket.IO Client on the frontend and Python Flask with Flask-SocketIO on the backend, along with the browser Geolocation API, OpenStreetMap through Leaflet, and the Gemini API for limited severity analysis. Its flow was: User, Panic Button, Location, Flask backend, Socket.IO event, Responder dashboard. It also had a basic map, alerts, a responder interface and chat.That prototype proved the idea but had clear limitations. Problem StatementDuring an emergency, communication and coordination become fragmented. The person in trouble must report what happened, explain where they are, find the right kind of help, describe the situation and wait for a response, often while stressed or injured. Responders, on the other side, need the location, severity, details, a way to reach the person, and clear information about who is already handling the case. Without a single shared system, information is scattered across phone calls and messages, duplicate responses are possible, and there is no reliable record afterwards.WhoWhat they struggle with todayWhat CrisisConnect gives themPerson in needExplaining location and situation under stress; not knowing if help is comingOne-press SOS, automatic location, live status and responder trackingResponderIncomplete information; unclear who else is respondingStructured incident details, map location, exclusive acceptance, direct chatAdministratorNo overview; hard to reassign or auditLive dashboard, assignment tools, analytics, permanent history4. User Stories and Acceptance CriteriaA user story is written as "As a [role], I want [goal], so that [benefit]". Acceptance criteria are the checks that decide whether it is done. Use these as test cases later.US-01: Send an SOS quickly so that help is alerted without filling a formRole: USERGiven I am logged in, when I press SOS and allow location, then an incident with isSOS = true and severity HIGH or CRITICAL is created.The incident status is PENDING and I see a confirmation with an incident number.Eligible responders receive the alert within about 2 seconds.If location is denied, the SOS is still created and I am asked for an address.US-02: File a detailed report so that responders get contextRole: USERI can choose a category, add a description and my location.Invalid input (empty description, unknown category) is rejected with a clear message.The severity shown to me is decided by the system, not chosen by me.US-03: Track my incident so that I know help is on the wayRole: USERI see the current status and, once accepted, the responder's name.Status changes appear without refreshing the page.After acceptance I see the responder moving on the map (Core+).US-04: Cancel my incident if the emergency is overRole: USERI can cancel while the status is PENDING, ASSIGNED or ACCEPTED.I cannot cancel once the status is IN_PROGRESS or later.The responder (if any) is notified and becomes available again.US-05: Go online and see incoming incidentsRole: RESPONDEROnly verified responders can go ONLINE.When ONLINE, I see new incidents sorted by severity then time.When OFFLINE, I receive no new alerts.US-06: Accept an incident so that I can respondRole: RESPONDERWhen I accept, the incident becomes ACCEPTED and assigned to me, and my status becomes BUSY.If another responder accepted first, I see "already taken" and nothing changes.The user is notified immediately.US-07: Update progress and resolve the incidentRole: RESPONDERI can move ACCEPTED to IN_PROGRESS and IN_PROGRESS to RESOLVED only.On RESOLVED, resolvedAt is stored, my status returns to ONLINE, and the chat closes.US-08: Verify responders so that only trusted people receive incidentsRole: ADMINI see a list of unverified responders and can approve or reject with a note.An unverified responder cannot go ONLINE or accept incidents.US-09: Assign or reassign an incident when nobody has acceptedRole: ADMINI can assign a verified, ONLINE responder to a PENDING incident.I can reassign an ASSIGNED incident; the previous responder is notified.Every change is recorded in the incident history with my name.US-10: See the system at a glanceRole: ADMINThe dashboard shows active, critical and resolved-today counts and available responders.Critical unassigned incidents are visually highlighted.US-11: Chat inside an incident so that we can coordinateRole: USER / RESPONDERMessages appear in real time for both participants and are saved.A user who is not part of the incident can neither read nor send messages.9. Feature SpecificationsEach feature below is described with the same template: purpose, actor, preconditions, input, processing, output, data touched, API and real-time involvement, and edge cases. Reuse this template when you write code explanations.9.1 Emergency SOSPurposeLet someone in danger request help in one action.ActorUSERPreconditionsLogged in; location permission preferred but not required.InputPressing SOS; browser coordinates (latitude, longitude); optional note.Processing1. Client captures location.2. Backend validates, sets isSOS = true and computes severity (HIGH, or CRITICAL if a life-threat indicator is set).3. Backend generates incident number, saves incident as PENDING with first statusHistory entry.4. Backend finds eligible ONLINE verified responders (nearby first) and notifies them; notifies admins if CRITICAL.OutputIncident created; user sees incident number and PENDING status; responders and admins receive a real-time alert.Data touchedincidents (insert), counters (increment), notifications (insert).API / real-timePOST /api/incidents; events incident:new, notification:new.Edge casesLocation denied; GPS inaccurate; user repeatedly pressing SOS (rate limit and duplicate detection); no responders online (stays PENDING, admins alerted); server error (user sees retry option and the emergency-number notice).9.2 Manual Emergency ReportPurposeProvide a detailed report when time allows.ActorUSERInputCategory, description, location, optional checklist answers (for example conscious, breathing), optional image.ProcessingValidate input; compute severity from category and checklist; save as PENDING; notify eligible responders.OutputIncident number and status; alerts to responders.Edge casesMissing or too-long description; unsupported category; oversized or wrong-type image; location missing (manual address).9.3 Responder Accepts an IncidentPurposeGive one responder exclusive ownership of an incident.ActorRESPONDER (verified and ONLINE)PreconditionsIncident is PENDING (self-claim) or ASSIGNED to this responder.ProcessingA single atomic database update changes status to ACCEPTED and sets assignedResponder only if the status is still PENDING (or ASSIGNED to this responder). If no document matches, the request fails with "already taken".OutputIncident ACCEPTED; responder becomes BUSY; user and admins notified; incident removed from other responders' lists; chat room opens.Edge casesTwo responders accept simultaneously; incident cancelled a moment earlier; responder goes offline between click and server processing.9.4 Status Update and ResolutionPurposeKeep everyone informed and close the incident correctly.ActorAssigned RESPONDER (or ADMIN)ProcessingCheck that the transition is allowed from the current status; write the new status and statusHistory entry; if RESOLVED set resolvedAt, free the responder, close chat and stop location sharing.OutputUpdated incident; real-time event to the incident room; notification to the user.Edge casesIllegal jump (ACCEPTED straight to RESOLVED is not allowed); responder not assigned to this incident; duplicate requests.9.5 Incident ChatPurposeLet the user and responder coordinate details (for example "I am near the main gate").ActorsIncident creator, assigned responder (admins may observe)ProcessingSocket handshake authenticated; socket joins incident room only after a participant check; each message is validated, saved, then broadcast to the room.Edge casesClosed incident; message too long; reconnect (missed messages loaded over REST); user removed from incident after reassignment.9.6 Live Responder LocationPurposeLet the user see help approaching.ActorRESPONDER device, USER viewerProcessingWhile ACCEPTED or IN_PROGRESS, the responder client sends coordinates every few seconds; the server validates the sender, updates the responder's latest location and forwards the point to the incident room only.Edge casesGPS permission denied; weak signal; updates too frequent (throttle); sharing must stop on close.9.7 Responder Verification and Admin AssignmentPurposeEnsure only trusted responders get incidents; ensure no incident is left unattended.ActorADMINProcessingVerification sets verificationStatus. Assignment checks the responder is verified and ONLINE, sets status ASSIGNED, notifies the responder, and records the action.Edge casesAssigning an OFFLINE or BUSY responder; assigning to a closed incident; two admins acting at once (same atomic-update rule).9.8 NotificationsPurposeMake important changes impossible to miss.ProcessingA notification service creates a notification record for each target user and emits it to that user's socket room; the client shows a counter and list.Edge casesUser offline when the event happens (they see it from the database on next login); duplicates.10. Business RulesBusiness rules are decisions the system must always obey, independent of the screen being used. Most of them become backend service logic.IDRuleBR-01Role is never accepted from the client. Public sign-up creates USER only.BR-02Severity is always computed or validated by the backend. Only an ADMIN may override it, and the override is logged.BR-03An incident has exactly one assigned responder at a time.BR-04Only a verified, ONLINE responder may receive or accept incidents.BR-05Status transitions follow the allowed-transition table; anything else is rejected.BR-06RESOLVED, CANCELLED and REJECTED are terminal; a terminal incident cannot be changed.BR-07A USER may cancel only before IN_PROGRESS; an ADMIN may cancel at any non-terminal status.BR-08A user may see only their own incidents; a responder only incidents available to them or assigned to them; an admin all incidents.BR-09Chat and live location exist only for the participants of an active incident.BR-10A responder with an active incident is BUSY and receives no new alerts.BR-11Suspended accounts cannot log in, send events or receive alerts.BR-12Responders who declined an incident are not offered it again.BR-13Every status change is recorded with actor and time. GlossaryTermMeaningIncidentA tracked emergency record with owner, category, severity, status, location and history.SOSA fast incident created with minimal input and high priority.ResponderA verified person who handles incidents.SeverityLOW, MEDIUM, HIGH or CRITICAL priority computed by the backend.Lifecycle / state machineThe fixed set of statuses an incident can have and the allowed moves between them.Atomic updateA database update that checks and changes data in one indivisible step, preventing race conditions.AuthenticationProving who you are (login).AuthorizationDeciding what you are allowed to do (roles, ownership).RBACRole-based access control.JWTJSON Web Token, a signed token used to identify a logged-in user.bcryptA slow, salted password-hashing algorithm.RESTRequest-response API style over HTTP.WebSocket / Socket.IOA persistent two-way connection (with a library) for real-time events.RoomA Socket.IO group of connections that receive the same events (one per incident).GeoJSONA standard JSON format for geographic points; coordinates are [longitude, latitude].2dsphere indexA MongoDB index enabling distance and "near" queries on GeoJSON data.MVPMinimum viable product: the smallest version that delivers the core value.17.
