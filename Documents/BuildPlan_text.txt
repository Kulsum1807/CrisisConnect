Part 1: Project Context Block (paste first, every time)

PROJECT: CrisisConnect (the name is exactly "CrisisConnect"; never add "2.0").

WHAT: A MERN real-time emergency response and incident management platform.

Citizens report emergencies (SOS or detailed report); verified responders are alerted

in real time; one responder accepts; user and responder share live status, chat and

responder location until resolved; admins verify responders, assign incidents, see

analytics. It is a placement project: I must understand and explain every line.

 

ROLES: USER (citizen), RESPONDER (verified), ADMIN.

CATEGORIES: MEDICAL, FIRE, ACCIDENT, CRIME_SECURITY, NATURAL_DISASTER,

            MISSING_PERSON, OTHER.   SEVERITY: LOW, MEDIUM, HIGH, CRITICAL.

STATUS: PENDING -> ASSIGNED -> ACCEPTED -> IN_PROGRESS -> RESOLVED;

        side exits CANCELLED, REJECTED. Terminal: RESOLVED, CANCELLED, REJECTED.

 

STACK: MongoDB Atlas + Mongoose, Express, React (Vite), Node.js (ES modules),

  Socket.IO, JWT (httpOnly cookies), bcrypt, Zod (validation), Tailwind CSS,

  React Router, Axios, Leaflet + React Leaflet (OpenStreetMap), Recharts,

  Jest + Supertest + mongodb-memory-server, Vitest + React Testing Library,

  helmet, cors, cookie-parser, express-rate-limit, dotenv, morgan + pino,

  ESLint + Prettier + nodemon, Git/GitHub.

 

ARCHITECTURE: layered monolith. routes -> middleware (protect, authorize, validate)

  -> controllers (thin) -> services (ALL business rules) -> Mongoose models.

  Socket handlers also call the same services. app.js builds the Express app (no

  listen); server.js starts HTTP + Socket.IO + DB. REST for commands, Socket.IO for

  pushing events. Database is the source of truth; after reconnect re-fetch via REST.

 

GROUND RULES:

1. Backend decides role, severity, status transitions, ownership. Never trust the

   client for these. Public register always creates USER; admin made by seed script.

2. Every status change goes through ONE function transitionIncident using an

   allowed-transitions map and a conditional update (atomic). Claim = findOneAndUpdate

   with { _id, status: "PENDING" }; null result => 409 ALREADY_TAKEN.

3. Ownership checks in services. Another user's incident returns 404 (not 403).

4. Never return password, refreshTokenHash or stack traces. password select:false.

5. Tokens: access (~15 min) + refresh (~7 days) in httpOnly cookies; refresh hash

   stored on the user; rotation on refresh; logout clears cookies and the hash.

6. GeoJSON order is [lng, lat]; Leaflet order is [lat, lng]. Convert in one utility.

7. AI features are optional and never required for the core flow.

8. Scope tiers: MVP first, then Core+, then Stretch. No features outside the phase.

 

API ENVELOPE: success { success:true, message, data }

  error { success:false, message, code, errors? }

ERROR CODES: VALIDATION_ERROR 400, UNAUTHENTICATED 401, TOKEN_EXPIRED 401,

  FORBIDDEN 403, ACCOUNT_SUSPENDED 403, NOT_FOUND 404, DUPLICATE 409,

  INVALID_TRANSITION 409, ALREADY_TAKEN 409, RESPONDER_UNAVAILABLE 409,

  RATE_LIMITED 429, SERVER_ERROR 500.

LISTS: ?page=1&limit=20 (max 100) -> data { items, page, limit, total, totalPages }.

 

BACKEND FOLDERS (backend/src): config, constants, models, validators, middleware,

  routes, controllers, services, sockets, utils, app.js, server.js; plus scripts/

  (seedAdmin.js) and tests/.

FRONTEND FOLDERS (frontend/src): components (common, layout, incidents, map, chat,

  admin), pages (public, user, responder, admin), layouts, context (AuthContext,

  SocketContext), hooks, services (api.js + per-resource), sockets, routes

  (ProtectedRoute, RoleRoute), constants, utils.

 

ENV (backend): NODE_ENV, PORT, MONGO_URI, JWT_ACCESS_SECRET, JWT_REFRESH_SECRET,

  ACCESS_TOKEN_TTL, REFRESH_TOKEN_TTL, CLIENT_URL, COOKIE_SAMESITE, COOKIE_SECURE,

  ALERT_RADIUS_KM, CLAIM_TIMEOUT_SEC.  ENV (frontend): VITE_API_URL, VITE_SOCKET_URL.

 

HOW TO ANSWER: give every file with its full path and complete code; then the exact

commands to run and test; then tests to add; then a short plain-language explanation

of why each piece exists; then notes I should add to brain.md (decisions, pitfalls).

Ask me if something is ambiguous. Do not invent features. Keep code simple and

readable (no clever tricks); I am a student who must explain it in interviews.



Note

Defaults chosen in this block: ES modules, Zod, Tailwind, deploy as a single service (Express serves the React build). If you decide differently, edit this block once and every later command follows.

Reference B: Lifecycle and severity

TRANSITIONS (from -> to : actor : guard)

 new -> PENDING : system : valid input

 PENDING -> ASSIGNED : ADMIN : responder VERIFIED, ONLINE, not in declinedBy

 PENDING -> ACCEPTED : RESPONDER claim : verified, ONLINE, atomic on status=PENDING

 ASSIGNED -> ACCEPTED : assigned RESPONDER

 ASSIGNED -> PENDING : assigned RESPONDER decline or ADMIN reassign; add declinedBy

 ACCEPTED -> IN_PROGRESS : assigned RESPONDER

 IN_PROGRESS -> RESOLVED : assigned RESPONDER or ADMIN; set resolvedAt; responder

     ONLINE; chat closes; location sharing stops

 PENDING/ASSIGNED/ACCEPTED -> CANCELLED : creator USER or ADMIN (USER not after

     IN_PROGRESS); free responder; store reason

 IN_PROGRESS -> CANCELLED : ADMIN only, reason required

 PENDING -> REJECTED : ADMIN, reason required

 Every transition appends statusHistory {status, changedBy, at, note}.

 Accept sets responder BUSY. Resolve/cancel sets responder ONLINE.

 

SEVERITY (backend only; client sends inputs)

 SOS -> HIGH; CRITICAL if not breathing / unconscious / severe bleeding / life threat

 Medical manual -> CRITICAL for those answers; HIGH if in pain; else MEDIUM

 Fire, Natural Disaster -> HIGH

 Crime/Security -> HIGH if inDangerNow else MEDIUM

 Accident -> HIGH if injuries else MEDIUM

 Missing Person, Other -> MEDIUM

 Admin may override with reason (audited).

 

ALERTING: find ONLINE VERIFIED responders near incident ($near, start 5 km), exclude

 BUSY and declinedBy; if nobody accepts within CLAIM_TIMEOUT_SEC widen radius

 (10, 25 km) and alert admins.

Reference D: Socket.IO

Connect with credentials; handshake verifies the access-token cookie (reject if

invalid or suspended). Auto-join: user:<id>; responders:online (verified ONLINE);

admins. Incident room incident:<id> only after participant (creator, assigned

responder) or admin check.

SERVER -> CLIENT

  incident:new {incidentId, incidentNumber, category, severity, isSOS, location}

  incident:updated {incidentId, status, assignedResponder, severity, at}

  incident:taken {incidentId}

  responder:location {incidentId, lat, lng, at}

  chat:message {_id, incidentId, senderId, senderName, text, createdAt}

  notification:new {_id, type, title, message, relatedIncident, createdAt}

  error:event {code, message, event}

CLIENT -> SERVER

  incident:join {incidentId} ; incident:leave {incidentId}

  chat:send {incidentId, text}  (participant, incident active, 1-500 chars)

  responder:location {incidentId, lat, lng} (assigned responder; ACCEPTED or

     IN_PROGRESS; valid coords; throttled to one per ~5 s)

Responder disconnect: grace 30-60 s then OFFLINE. Client on reconnect: re-fetch

incident, messages, notifications over REST and rejoin rooms.
