CrisisConnect is a real-time emergency response and incident management platform that connects people who need help with available responders and administrators. Users can trigger an SOS or file a detailed report, share their location, chat with the assigned responder and track progress. Responders see incoming incidents, accept them, update status and share live location. Administrators monitor the whole system, verify responders, assign incidents and view analytics.

Purpose: a technically strong, explainable prototype that demonstrates authentication, authorization, database design, REST APIs, real-time communication, geolocation, maps, role-based access control, notifications and dashboards. It is not meant to replace professional emergency infrastructure.

Disclaimer (to show in the app): CrisisConnect is a prototype and does not replace official emergency services. In an emergency, contact the local emergency number (112 in India).

Core flow

Emergency reported -> Location captured -> Incident created (PENDING)

  -> Available responder notified -> Responder accepts

  -> Real-time coordination (status, chat, live location)

  -> Incident resolved -> Full history stored

3. Problem Statement and Objectives

In an emergency, communication becomes fragmented. A person must report the situation, explain where they are, find help, describe what is happening and wait for updates, while responders need the location, severity, details, a way to reach the person and a clear record of who is handling what. CrisisConnect provides one centralized system for reporting, coordination, location tracking and communication.

Objectives

Build a full-stack MERN application with secure authentication and role-based authorization.

Provide SOS and detailed manual reporting with persistent storage in MongoDB.

Provide real-time incident updates, responder assignment, incident-specific chat, live responder location and notifications.

Provide responder and admin dashboards with analytics and incident history.

Follow a modular backend and reusable frontend architecture with validation and centralized error handling.

Apply security best practices and deploy in a production-like environment.

Understand every part well enough to explain and defend it in interviews.

RESOLVED, CANCELLED and REJECTED are terminal. Every transition is validated on the backend, stamped into a statusHistory array (status, changedBy, time, note), and broadcast over Socket.IO.

Concurrency rule: claiming uses one conditional update, for example findOneAndUpdate({ _id, status: "PENDING" }, { status: "ACCEPTED", assignedResponder }). If it returns null, someone else got there first and the responder sees "already taken".

8. Location and Maps

Browser Geolocation API -> lat/lng -> React -> REST API -> MongoDB (GeoJSON Point)



Storage: location is a GeoJSON Point { type: "Point", coordinates: [lng, lat] } (note the longitude-first order) with a 2dsphere index. This enables $near / $geoNear queries for nearby responders within a radius.

Map (React Leaflet): user marker, responder marker, incident marker, severity-colored markers, selected incident, auto-centering, live responder movement. Route and distance are a stretch item.

Live responder location: while handling an active incident, the responder device sends periodic updates (throttled, for example every 5 to 10 seconds) through Socket.IO to the incident room, so the user sees the responder approach. Sharing starts on ACCEPTED and stops on RESOLVED or CANCELLED.

Note: the Geolocation API requires HTTPS in production (localhost is exempt).

Rules

Socket authentication: the JWT is verified in the connection handshake; unauthenticated sockets are rejected.

Rooms: one room per incident (incident:<id>), plus per-user rooms (user:<id>) and a responders:online room. A socket may join an incident room only if it is the creator, the assigned responder or an admin.

Reconnect strategy: sockets can drop on mobile networks, so on reconnect the client re-fetches current incident state and missed messages over REST. Socket events are hints; the database is the source of truth.

Disconnect handling: a responder who disconnects is marked OFFLINE after a grace period.

Scaling note: a single Socket.IO server is fine for this project; scaling to multiple instances would need a Redis adapter (future scope).

10. Incident-Specific Chat and Notifications

Incident #1001

  |-- User

  |-- Assigned Responder

  `-- Messages (user -> responder, responder -> user, ...)



Each incident has its own chat room instead of one global chat. Messages carry message ID, incident ID, sender ID, text, timestamp and read status, and are persisted in MongoDB. Chat opens when a responder is assigned or accepts, and becomes read-only after the incident is closed. History is fetched over REST and authorized by incident participation.

Notifications are in-app, delivered through Socket.IO and persisted in MongoDB with read/unread state. Examples: "Responder Rahul accepted your emergency" (user), "New high-priority incident reported nearby" (responder), "Your incident is now In Progress" (user), "Critical incident requires assignment" (admin). SMS and email are out of scope for the first version.

12. Admin Dashboard and Analytics

Live metrics: total users, total responders, active incidents, critical incidents, available responders, resolved today, and a recent-incidents list (incident number, category, severity).

Analytics (stretch beyond the basic counts): incidents by category, severity and status; daily and weekly counts; average response time (created to accepted); average resolution time (created to resolved); responder activity. 16. Authentication and Authorization

Register: validate -> check email -> bcrypt hash -> save user (role = USER)

Login:    email + password -> find user -> compare hash -> issue token(s)

Request:  token -> auth middleware -> load user -> role middleware -> controller



Authentication answers "Who are you?"; authorization answers "What may you do?". USER: create and view own incidents. RESPONDER: view and act on assigned or available incidents. ADMIN: manage users, responders and all incidents. Backend authorization is mandatory.

Token strategy [Decision to discuss in Phase 5]

Option

Pros

Cons

Access JWT in localStorage

Simplest

Readable by any injected script (XSS)

Access JWT in httpOnly cookie

Not readable by JavaScript; logout can clear it

JWTs are stateless, so "logout" means clearing the cookie and revoking the refresh token. Passwords are hashed with bcrypt (never plain text), and sockets reuse the same token for handshake authentication.

18. Security

Security is part of the design, not an afterthought, and starts in Phase 5.

Passwords and tokens: bcrypt hashing, secure token strategy, secrets only in environment variables.

Access control: role-based authorization plus ownership checks. A user must not be able to PATCH another user's incident by guessing its ID; the same checks apply to chat history and socket events.

Input safety: schema validation on every request (Zod, Joi or express-validator), NoSQL-injection sanitization, request size limits.

HTTP hardening: Helmet, CORS limited to the known client URL, rate limiting on login and SOS creation, and false-alarm abuse handling (admins can suspend repeat offenders).

Uploads: type and size validation, restricted storage, no executable files.

Privacy: location is sensitive. Responder location is shared only with participants of an active incident, sharing stops when the incident closes, and responder phone numbers are not exposed broadly. Define how long incident data is kept.

Errors: secure, consistent responses with no stack traces or internals leaked to the client.

19. Error Handling and Configuration

A centralized error middleware returns one consistent response shape. Error categories: validation, authentication, authorization, not found, duplicate data, database and server errors. A custom AppError class lets services throw meaningful errors; the frontend maps them to friendly messages.

Environment variables (never hardcoded; separate development and production values): MONGO_URI, JWT_SECRET, PORT, CLIENT_URL, API_URL, plus refresh-token secret and image-storage keys if used. Provide a .env.example and keep real .env files out of Git.

25. Interview Preparation

30-second explanation (draft)

"CrisisConnect is a real-time emergency response platform built on the MERN stack. Users can trigger an SOS or report an incident with their location; nearby verified responders are notified over Socket.IO, one accepts, and the user then tracks the responder and chats with them.
