1. Design Principles and Decisions Log

1.1 Principles

Principle

Meaning in this project

Backend is the authority

The client sends inputs; the server decides role, severity, status transitions and permissions.

Database is the source of truth

Socket events are notifications that something changed; after reconnecting, clients re-fetch from the database.

Deterministic core

The emergency workflow uses fixed rules. AI, if added, only suggests and is never required.

Least privilege

Each role, and each socket, sees and does only what it needs.

Fail safe for emergencies

If something optional fails (location, image, AI), the SOS still goes through.

Simple and explainable

Prefer a clear design you can explain over a clever one.

Consistent contracts

One response envelope, one error format, one naming style.



1.2 Decisions log

These choices were made in this document. Each can be changed, but change the affected sections together.

ID

Decision

Reason

D-01

Initial incident status is PENDING; there is no separate CREATED state.

CREATED and PENDING existed for milliseconds; one state is simpler and equally informative.

D-02

Responders may self-claim a PENDING incident, and admins may also assign.

Self-claim is fast; admin assignment covers unattended or critical cases.

D-03

Latest responder location is stored on the responder's user document.

Avoids an extra collection; a TTL trail collection is a Stretch option.

D-04

Access token (short-lived) plus refresh token, both in httpOnly cookies.

Safer than localStorage tokens; supports real logout by revoking the refresh token.

D-05

Locations use GeoJSON points with a 2dsphere index.

Enables nearby-responder queries.

D-06

Incident number is a sequential counter with a prefix (for example CC-1001).

Easy for humans to quote; created from a counters collection.

D-07

API responses use one envelope with success, message and data or error.

Predictable frontend handling.

D-08

IDs in URLs are MongoDB ObjectIds; list endpoints are paginated.

Standard, simple.

3. Incident State Machine Design

An emergency is a lifecycle, not a flag. The server owns every transition.

   (create) ---> |      PENDING      | ---- admin ----> REJECTED

                 +----+----------+---+

            admin     |          | responder self-claims

            assigns   v          v

                 +----------+  +-----------+

                 | ASSIGNED |->| ACCEPTED  |   (assigned responder accepts)

                 +----+-----+  +-----+-----+

        decline/      |              | responder starts

3.2 Implementation approach

Keep an allowedTransitions map in one service file: { PENDING: [ASSIGNED, ACCEPTED, CANCELLED, REJECTED], ASSIGNED: [ACCEPTED, PENDING, CANCELLED], ACCEPTED: [IN_PROGRESS, CANCELLED], IN_PROGRESS: [RESOLVED, CANCELLED(admin)] }.

Every transition goes through one function, for example transitionIncident(incidentId, toStatus, actor, note). Controllers and sockets never change status directly.

The function checks the map, checks the actor guard, performs a conditional update (match _id and expected current status), pushes a statusHistory entry in the same update, then triggers notifications.

If the conditional update matches nothing, return 409 Conflict ("incident state changed").

// claim example (concept)

Incident.findOneAndUpdate(

  { _id: id, status: "PENDING" },

  { $set: { status: "ACCEPTED", assignedResponder: responderId },

    $push: { statusHistory: { status: "ACCEPTED", changedBy: responderId, at: now } } },

  { new: true }

);   // null result => someone else got there first



Interview angle

"How did you design the incident state machine?" Explain the status list, the allowed-transition map, actor guards, the single transition function, the conditional update that prevents races, and the statusHistory audit trail.

4.2 Finding and alerting responders

1. Incident saved as PENDING.

2. Query users where role=RESPONDER, verified, availability=ONLINE,

   not in incident.declinedBy, and currentLocation $near incident.location

   within radius R (start: 5 km).

3. Emit incident:new to those responders (their user rooms).

4. If no one accepts within T seconds (start: 60): widen radius (10 km, then 25 km)

   and notify admins. Repeat up to a maximum, then leave PENDING with an admin alert.



A responder whose location is unknown or stale (older than a few minutes) is still alerted if no nearby responder exists, so nobody is excluded just because of GPS issues. R and T are configuration values, not hard-coded.

4.3 Incident number generation

A counters document { _id: "incident", seq: N } is incremented atomically with $inc when an incident is created. The new value becomes the incident number, formatted like CC-1001. This avoids duplicates when two incidents are created at the same moment. (MongoDB ObjectId remains the true primary key.)

6. Authentication and Authorization Design

6.1 Registration

POST /api/auth/register  { name, email, phone, password }

  -> validate (format, password strength)

  -> email already exists? -> 409

  -> bcrypt.hash(password, 10..12 rounds)

  -> create user with role USER (any role in body is ignored)

  -> respond 201 with user (no password)

Responders use a separate sign-up that creates role RESPONDER with verificationStatus PENDING. Admins are created only by a seed script.

6.2 Login and token handling

Item

Design

Access token

JWT containing user id and role; lifetime about 15 minutes; sent as an httpOnly, secure, sameSite cookie.

Refresh token

Random or JWT value; lifetime about 7 days; httpOnly cookie restricted to the refresh path; its hash is stored in the user document.

Login

Find user by email (select password); reject inactive; bcrypt.compare; issue both tokens; return user without password. Use one generic error ("Invalid credentials") for wrong email or password.

Refresh

Verify the refresh token and compare its hash; issue a new access token (and rotate the refresh token); on mismatch, clear cookies and force login.

Logout

Clear both cookies and clear refreshTokenHash.

Cross-origin setup

CORS with credentials: true and an explicit origin; axios withCredentials: true; Socket.IO connects with credentials.



Why this design

A token in localStorage can be stolen by any injected script (XSS). An httpOnly cookie cannot be read by JavaScript. The cost is thinking about CSRF, reduced here by sameSite and by using JSON-only state-changing endpoints. JWTs are stateless, so a real logout needs the refresh-token hash on the server.

6.3 Middleware chain for a protected request

Request -> protect (read cookie, verify JWT, load user, reject if inactive)

        -> authorize(...roles) (check req.user.role)

        -> validate(schema) (check body, params, query)

        -> controller -> service (ownership checks, business rules) -> model

8. Real-Time Event Contract (Socket.IO)

REST changes data; Socket.IO tells people it changed. Each event below lists direction, payload and who may receive it. Payloads are small; clients re-fetch details over REST when needed.

8.1 Connection and rooms

Item

Design

Authentication

The access-token cookie is verified in the Socket.IO connection middleware. Failed verification rejects the connection; the identity (userId, role) is attached to the socket.

Personal room

On connect the socket joins user:<userId> for notifications and direct alerts.

Role rooms

Verified ONLINE responders join responders:online; admins join admins.

Incident room

incident:<incidentId>, joined only after the server confirms the user is the creator, the assigned responder or an admin.

Disconnect

Responder gets a grace period (for example 30 to 60 seconds) before being marked OFFLINE.

Reconnect

Client re-fetches current incident and unread notifications over REST, then rejoins rooms.

9. Validation Design

Validation runs in middleware (a schema library such as Zod, Joi or express-validator) before the controller, and again in Mongoose schemas as a safety net. Unknown fields are stripped, which also blocks mass-assignment attacks (for example a client sending role or severity).

Input

Rules

name

Required, trimmed, 2 to 60 characters

email

Required, valid format, lowercase, unique

phone

Required, valid phone pattern (digits, optional country code), 10 to 15 digits

password

Required, minimum 8 characters, at least one letter and one number; maximum length enforced to avoid bcrypt abuse

category

Must be one of the defined enum values

description

Required for manual reports, up to 1000 characters; HTML stripped

location

lat between -90 and 90, lng between -180 and 180; both numbers

status (update)

Must be a valid status; transition checked separately by the state machine

chat text

1 to 500 characters, trimmed

ObjectId params

Must be valid ObjectIds, otherwise 400 (not a server crash)

Positive integers; limit capped at 100

image (Stretch)

Type jpg/png/webp only, maximum 5 MB, renamed on save

Everything

Strip unknown fields; sanitize against NoSQL operator injection ($ and . keys)

10. Error Handling Design

Services throw a custom AppError(message, statusCode, code). A single error middleware at the end of the chain converts any error (AppError, Mongoose validation or duplicate-key, JWT, unknown) into the standard error envelope. Unknown errors are logged with details but the client receives only a generic message.

11. UI/UX Design

11.1 Design principles

Emergency first: the primary action (SOS) is the largest, most visible element on the user dashboard.

Severity is instantly readable: colour, icon and text label together (never colour alone).

Few taps, little typing: especially for the user in danger.

Calm clarity for responders and admins: dense information, but clearly grouped and sorted by priority.

Always show state: loading, empty, error, offline and connection-lost indicators.

Mobile-first: users and responders are on phones; admins mostly on desktop.

12. Security Design

Threat

Example

Mitigation in this design

Broken access control (IDOR)

User calls PATCH /api/incidents/:id for someone else's incident

Ownership and role checks in the service layer on every route and socket event; 404 for hidden resources

Privilege escalation

Client sends role: ADMIN in the register body

Role ignored; set only by the server; schema validation strips unknown fields

Mass assignment

Client sends severity or status in create body

Whitelist of accepted fields; severity and status computed on the server

Credential theft

Database leak exposes passwords

bcrypt hashes; password select: false

Token theft (XSS)

Script reads a token from localStorage

httpOnly cookies; output escaping by React; Helmet headers

CSRF

Malicious site triggers requests with cookies

sameSite cookies, restricted CORS origin, JSON-only endpoints

Brute force

Guessing passwords

Rate limiting on login; generic error message

NoSQL injection

Body contains { "$gt": "" } operators

Schema validation and sanitization of $ and . keys

Abuse and spam

Repeated false SOS requests

Rate limiting and duplicate detection; admin reject and suspend

Socket abuse

Joining a room of another incident; spoofing sender

Handshake authentication; participant check before join; identity from socket only

Location privacy

Anyone viewing responder or user location

Visible only to incident participants and admins; sharing stops when incident closes

Malicious upload

Executable disguised as image

Type and size checks, renamed files, no execution from upload folder (Stretch feature)

Information leakage

Stack traces in responses

Generic 500 message; details only in server logs

Secrets exposure

Keys committed to Git

Environment variables, .gitignore, .env.example

Sender client --chat:send {incidentId, text}--> Socket middleware (identity known)

  -> participant + status check -> validate text -> save message (MongoDB)

  -> emit chat:message to room incident:<id> -> both clients append message



13.3 Live location

Responder device (every 5-10 s) --responder:location--> server

  -> caller is assignedResponder? status ACCEPTED/IN_PROGRESS? throttle ok?

  -> update responderProfile.currentLocation -> emit to room incident:<id>

  -> user map moves the responder marker

Socket drops -> client shows "reconnecting" banner

Socket reconnects -> client: GET /api/incidents/:id, GET /api/notifications,

                      GET messages since last id -> rejoin rooms -> UI is correct again

Topic

Remember

State machine

One transition function, an allowed-transition map, actor guards, conditional update, statusHistory.

Atomic claim

findOneAndUpdate({ _id, status: PENDING }, ...) returns null for the loser, which becomes a 409.

Severity

Client sends inputs; server decides; admin override is logged.

GeoJSON

Coordinates are [lng, lat]; 2dsphere index; $near for nearby responders.

Auth

bcrypt hashing; short access token plus refresh token in httpOnly cookies; role from the database.

Authorization

Role middleware plus ownership checks in services; 404 to hide others' incidents.

Embedding vs referencing

Embed small bounded data (statusHistory, location); reference unbounded data (messages).

REST vs sockets

REST for operations; sockets for pushing change events; database is the source of truth.

Socket security

Handshake auth, participant check before join, identity from the socket.

Errors

AppError, one error middleware, one envelope, stable error codes.
