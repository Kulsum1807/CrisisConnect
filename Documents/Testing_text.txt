PART A: TESTING

1. Testing Strategy

1.1 Goals

Prove every MVP and Core+ requirement in the PRD works as specified.

Protect the parts where bugs are most dangerous: authorization, the incident state machine, exclusive claiming and real-time delivery.

Catch regressions automatically as the project grows, so changes never silently break old features.

Produce evidence (test results, a manual test log) that you can show and explain in interviews.

1.4 Coverage targets

Area

Target

Critical logic (transitions, claim, authorization, severity)

100% of branches covered by meaningful tests

Services overall

At least 80% line coverage

Controllers and routes

Every endpoint has a success test and at least one failure test

Frontend

Key forms, guards and shared components; do not chase a percentage

Coverage is a guide, not a goal. A test that runs a line without asserting anything is worthless; prefer fewer tests with clear assertions.

Interview angle

"How did you test your project?" Name the pyramid, then give the two best examples: the parallel-claim concurrency test and the IDOR negative tests. Mention that tests run on an in-memory database so they are fast and safe.

test("only one responder can accept", async () => {

  const inc = await createIncident(users.asha);

  const [a, b] = await Promise.all([

12. Testing Interview Questions

Question

Strong answer outline

What is the difference between unit, integration and end-to-end tests?

Scope and speed: unit tests one function, integration tests several parts with a real database, E2E tests the whole system through the UI. Use many unit, fewer integration, few E2E.

How do you test code that uses a database?

Integration tests with an in-memory MongoDB and fresh data per test, never the real database.

How did you test the concurrent accept?

Fired parallel requests with Promise.all and asserted exactly one 200 and one 409, and exactly one history entry.

How do you test authorization?

Negative tests: for each endpoint call it as the wrong role and as the wrong owner and assert 403 or 404 with no data leaked.

How do you test WebSockets?

Connect multiple socket.io-client instances as different users and assert which receive which events; test rejected handshakes and room joins.

What is a regression test?

A test added after a bug is fixed so the bug cannot come back unnoticed.

What is mocking and when did you use it?

Replacing a dependency with a fake (for example the socket emitter or AI service) to isolate logic; avoid mocking the database in integration tests.

What would you add with more time?

CI pipeline, end-to-end tests with Playwright or Cypress, load tests, contract tests for the API.

13. Conventions

Item

Convention

Base URL

Development: http://localhost:5000/api. Production: your deployed origin + /api

Format

JSON request and response. Header: Content-Type: application/json (multipart only for image upload, Stretch)

Authentication

httpOnly cookies set by login (accessToken, refreshToken). Clients must send credentials: Axios withCredentials: true; fetch credentials: "include"; Postman keeps a cookie jar automatically

Success envelope

{ "success": true, "message": "text", "data": { ... } }

Error envelope

{ "success": false, "message": "text", "code": "ERROR_CODE", "errors": [ { "field": "email", "message": "Invalid email" } ] }  (errors only for validation)

Pagination

Request: ?page=1&limit=20 (limit max 100). Response data: { items, page, limit, total, totalPages }

Sorting and filters

?sort=-createdAt, ?status=PENDING&severity=HIGH&category=MEDICAL&from=2026-10-01&to=2026-10-31

Dates

ISO 8601 UTC, for example 2026-10-05T09:12:03Z

IDs

MongoDB ObjectId strings (24 hex characters); invalid format returns 400

Location input

{ "lat": 28.6139, "lng": 77.2090 } in requests; stored as GeoJSON [lng, lat]; responses return { "lat", "lng" } for convenience (decide once and keep consistent)

Ignored fields

Unknown or forbidden fields (role, severity, status, createdBy, incidentNumber, isActive) in request bodies are ignored or rejected

20. Socket.IO Reference

Connection: connect to the server origin with credentials so the access-token cookie is sent. In the browser: io(SOCKET_URL, { withCredentials: true }). An invalid or missing token rejects the connection (connect_error). After connecting the server automatically places the socket in user:<id> and the relevant role rooms.

20.1 Server to client

Event

Payload

Delivered to

incident:new

{ incidentId, incidentNumber, category, severity, isSOS, location: {lat,lng}, createdAt }

Eligible ONLINE responders; admins

incident:updated

{ incidentId, status, assignedResponder: { _id, name } | null, severity, at }

incident:<id> room; admins

incident:taken

{ incidentId }

Other eligible responders

responder:location

{ incidentId, lat, lng, at }

incident:<id> room

chat:message

{ _id, incidentId, senderId, senderName, text, createdAt }

incident:<id> room

notification:new

{ _id, type, title, message, relatedIncident, createdAt }

user:<id> room

error:event

{ code, message, event }

Only the emitting socket



20.2 Client to server

Event

Payload

Server checks and result

incident:join

{ incidentId }

Participant or admin, else error:event FORBIDDEN; joins incident:<id>

incident:leave

{ incidentId }

Leaves the room

chat:send

{ incidentId, text }

Participant, incident active, text 1 to 500 characters; saves, then emits chat:message

responder:location

{ incidentId, lat, lng }

Sender is assignedResponder; status ACCEPTED or IN_PROGRESS; valid coordinates; rate limited; updates profile and emits to room



Client usage example

const socket = io(import.meta.env.VITE_SOCKET_URL, { withCredentials: true });

socket.on("connect_error", err => { /* not logged in or token invalid */ });

socket.emit("incident:join", { incidentId });

socket.on("incident:updated", payload => { /* replace by id in state */ });

// cleanup in useEffect return:

return () => { socket.emit("incident:leave", { incidentId });

               socket.off("incident:updated"); };

21. Postman Guide

Item

Setup

Environments

Create "Local" (baseUrl = http://localhost:5000/api) and "Production" (baseUrl = deployed URL + /api)

Collection layout

Folders matching sections 14 to 19: Auth, Users, Incidents, Responders, Notifications, Admin

Cookies

Postman stores cookies per domain; log in once per role. Use separate Postman windows or environments (or cookie clearing) to switch between USER, RESPONDER and ADMIN

Variables

Save ids from responses: incidentId, responderId, userId

Negative requests

For each endpoint add requests that must fail: wrong role, other user's id, bad body

Export

Export the collection into the repository docs folder as living documentation
